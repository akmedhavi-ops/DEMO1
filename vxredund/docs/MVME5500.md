# Porting and bring-up: MVME5500 (VxWorks 6.9 / 7)

The core (`src/`) is OS-independent. VxWorks-specific code is limited to:

- `osal/rdn_osal_vxworks.c`: semaphores, tasks, time;
- `links/rdn_link_udp.c`: BSD sockets;
- `vxworks/rdn_vx_mvme5500.c`: VME window mapping, demo and shell commands.

The VxWorks sources are compile-checked against the VxWorks 6.9 kernel API
signatures. They have **not** been run on MVME5500 hardware as part of this
reference. Follow the checklist at the end.

## Board facts that matter

| Item | MVME5500 | Consequence |
|---|---|---|
| CPU | MPC7457 (PowerPC 74xx, big-endian) | `-mcpu=7450`. `RDN_MEM_BARRIER()` = `sync` |
| System controller | Marvell MV64360 | Snooping configuration decides whether VME-inbound writes are cache-coherent; see *Caches* |
| VME bridge | Tundra Universe II | A32 slave window (inbound) and master windows (outbound); posted writes keep their order |
| Ethernet | Gigabit port plus a 10/100 port | Use the Gigabit port as the dedicated redundancy link; the BSP names the interface (e.g. `gei0`) |
| Time base | Decrementer/TB at bus clock / 4 | Optional µs clock with `-DRDN_VX_USE_TIMEBASE -DRDN_VX_TB_HZ=<Hz>`; check the frequency in your BSP |

VxWorks 7: the code uses only APIs common to 6.9 and 7. Whether a VxWorks 7
BSP exists for MVME5500 depends on your board vendor and Wind River support.
The same sources build as a VxWorks 7 DKM or VSB layer on any VxWorks 7
target, e.g. a newer VME SBC (`vxworks/vx7/` holds layer templates).

## Topology

```
   +------------------ VME backplane (A32) -------------------+
   |                                                          |
 +-+--------------------+                  +------------------+-+
 | MVME5500  node 1     |                  | MVME5500  node 2     |
 |  slave win: DRAM ----+--> area 1 <------+-- master win (writes) |
 |  master win (writes)-+--> area 2 <------+-- slave win: DRAM     |
 |  gei0 192.168.100.1  |<==== GbE ======> |  gei0 192.168.100.2   |
 +----------------------+  crossover/VLAN  +-----------------------+
```

Each node **writes** into the peer's area and **reads** only its own memory.
VME reads are slow, non-posted cycles and are never issued.

## Configuration (BSP `config.h`)

1. **Reserve memory for the ring area** at the top of RAM:

   ```c
   #define USER_RESERVED_MEM  0x00010000   /* 64 KB >= rdn_link_vme_area_size(32, 1472) = 47 424 */
   ```

2. **Export it with the A32 slave window.** The window must cover
   `sysMemTop()` .. `sysMemTop() + USER_RESERVED_MEM`. On Motorola/Emerson
   PPC BSPs the relevant macros are typically `VME_A32_SLV_LOCAL`,
   `VME_A32_SLV_BUS` and `VME_A32_SLV_SIZE`; the names vary by BSP
   revision. Give each board a different `VME_A32_SLV_BUS`, e.g. by slot.
3. **Master window** (`VME_A32_MSTR_*`) must reach the peer's slave window.
   It must be mapped cache-inhibited and guarded in the MMU; the BSP default
   for VME space normally already is. `-mstrict-align` is set because
   unaligned access to cache-inhibited space faults on 74xx.
4. **Byte swapping.** The ring stores native-endian words. Both boards are
   PPC with the same BSP, so any *symmetric* Universe II swap configuration
   works. Do not pair boards of different endianness.
5. **Clock.** `sysClkRateSet(1000)` in `usrAppInit()` (1 ms tick), or build
   with `TIMEBASE=1`.
6. **Components:** `INCLUDE_SEM_BINARY`, `INCLUDE_SEM_MUTEX`,
   `INCLUDE_LOGGING`, BSD sockets / IPNET with UDP, `INCLUDE_CACHE_SUPPORT`.

rdnVmeAreaInit() converts addresses with `sysLocalToBusAdrs()` and
`sysBusToLocalAdrs()` in `VME_AM_EXT_SUP_DATA` (A32 supervisory data). It
prints this node's bus address, which you then configure on the peer.

## Caches

VME-inbound writes land in DRAM through the Universe II → PCI → MV64360
path. If PCI snooping is not enabled for that range, the CPU can read stale
cache lines. The board glue therefore installs
`cacheInvalidate(DATA_CACHE, …)` / `cacheFlush(DATA_CACHE, …)` hooks, which
the ring calls before reading its own area and after writing the peer's.
The hooks are harmless if the range is coherent. Alternatively, map the
reserved area cache-inhibited and set the hooks to `NULL`.

## Build

VxWorks 6.9 (command line, DKM):

```sh
wrenv -p vxworks-6.9
cd vxredund/vxworks/vx69 && make            # -> vxredund.out
```

Workbench: create a *Downloadable Kernel Module* project. Add the source
files listed in `vxworks/vx69/Makefile`, add `include/` and `src/` to the
include path, and use the `PPC32gnu` build spec.

VxWorks 7: add `vxredund/` as a VSB layer (`vxworks/vx7/layer.vsbl`,
`Makefile`, `cdf/40vxredund.cdf` are templates to adapt to your release),
or build the same file list as a DKM project.

## Run (target shell)

```
-> sysClkRateSet 1000
-> ld < vxredund.out
-> rdnDemoStart 1, "192.168.100.1", "192.168.100.2", 0, 0x08000000     (node 1)
-> rdnDemoStart 2, "192.168.100.2", "192.168.100.1", 0, 0x09000000     (node 2)
-> rdnShow
-> rdnSwitch          planned switchover (on the active)
-> rdnFault           inject a local fault (-> SAFE)
-> rdnReset           maintenance reset (SAFE -> DISCOVER)
-> rdnStop            graceful stop (relinquish)
```

The last two arguments are the offset of this node's area in the reserved
memory and the **peer's** A32 bus address, as printed by the peer's
`rdnDemoStart`. Pass `0` as the peer address to run over Ethernet only;
pass `NULL` IPs to run over VME only.

## Task priorities

| Task | Default | Note |
|---|---|---|
| `tRdnRx<l><n>` | 48 | One per link. Time-stamps arrivals; keep above application tasks |
| `tRdnMon` | 50 | Periodic monitor; its release jitter is `J` |
| `tNet0` | 50 (6.9 default) | UDP delivery depends on it. Do not starve it with higher-priority application load, or budget the delay in `L_max` |
| application | e.g. 60 | Runs `rdn_cycle_begin/end` |

## Bring-up checklist

1. Each board: `rdnDemoStart` with Ethernet only. Verify the roles, then run
   `rdnSwitch` in both directions.
2. VME only: verify that `rdnVmeAreaInit` prints valid addresses on both
   boards. Watch `rdnShow`: frames flow, with `crc` = `hdr` = 0.
3. Both links: pull the Ethernet cable. There must be no failover, and
   `link 0 up 0`. Re-plug; then do the same with the VME link disabled.
4. **Failover campaign.** Power-cycle or `reboot` the active at random
   phases, ≥ 100 times. Record `max_detect_us` / `max_takeover_us` on the
   survivor and compare against `rdn_timing_bound()`. Then re-derive `J`
   and `L_max` from the observed maxima, with margin.
5. **Load test.** Repeat step 4 with worst-case application, network and
   backplane load.
6. Partition test (both links cut, both CPUs alive): verify that the output
   interlock prevents dual output. Without an arbiter the software *will*
   report dual-active until the links recover (see SAFETY.md H1).
7. Enable the hardware watchdog, and verify that a hung `tRdnMon` resets the
   board and that its outputs drop.
